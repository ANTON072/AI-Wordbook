# /write-glossary

PRD(docs/001_product-requirements.md)・機能設計書(docs/002_functional-design.md)・技術仕様書(docs/003_architecture.md)・リポジトリ構造定義書(docs/004_repository-structure.md)・開発ガイドライン(docs/005_development-guidelines.md)を走査し、そこに登場するドメイン用語・UI 用語・コード命名語彙を抽出してユビキタス言語定義(docs/006_glossary.md)を作成する。

006 は同一概念に対する**表記ゆれを吸収する単一情報源（SSOT）**である。各概念について「正の表記」を1つ定め、混在していた別表記は「別名・禁止表記」に集約する。`docs-integration-reviewer` の用語不統一チェックはこの 006 を正として 001〜005 と照合するため、006 は照合の基準そのものになる。

**001〜005 本文は書き換えない。** 本コマンドがするのは 006 に正の表記を定義することだけで、001〜005 に残る表記ゆれの実際の修正は後段の `docs-integration-reviewer`（横断レビュー）に委ねる。

## スコープの境界

006 が定めるのは「用語の正表記・定義・コード識別子との対応」に限る。以下は上位ドキュメントで確定済みであり、006 では繰り返さない。

- 技術・ライブラリの選定とその根拠 → 003
- ディレクトリ・ファイルの物理配置、モジュール依存の方向 → 004
- コードをどう書くか（コーディング規約・コンポーネント設計・テスト戦略） → 005
- ユースケース・画面設計・データフロー・キー設計・ビジネスルール → 002

006 は「その概念を何と呼ぶか」だけを定め、その概念が何をするか・どう実装するかは書かない。

## 手順

### 1. ドキュメントの走査と用語抽出

- `find docs -maxdepth 1 -name '00[1-5]_*.md'` で 001〜005 のうち**存在するファイルだけ**を列挙し、それぞれ Read する（005 は未作成の可能性があるため、存在するものだけを対象にする）。
- 各ドキュメントから、命名対象となる次の3系統を機械的に洗い出す。
  - **ドメイン用語** — 英単語帳ドメインの概念語
  - **UI 用語** — Web 画面で使う表示・操作の語
  - **コード命名語彙** — 実装識別子・キー・型名・MCP ツール名など
- 同一概念に対して複数の表記が使われている箇所（表記ゆれ）を、出典とともに束ねる。

### 2. 正の表記の自動決定

抽出した同一概念の複数表記について、次の優先順で「正の表記」を1つ選ぶ。

1. 実装識別子・キー・型名と整合する表記を優先する（コードと文書で語が食い違わないようにする）
2. 上位ドキュメント群で最も頻出する表記を優先する
3. `doc-writing-style` 規範2に反する擬似ジャーゴン（一般語に独自の特別な意味を込めた語）を避ける

選ばれなかった表記は「別名・禁止表記」列に回す。原則は自動決定だが、どれを正とするか判断がつかない概念があればその場でユーザーに短く確認してよい。

### 3. テンプレートを読む

Read ツールで `.claude/skills/write-glossary/template.md` を読む。

### 4. ドラフト作成

抽出・決定結果をテンプレートの用語表に流し込み `docs/006_glossary.md` を書く。用語表は1概念1行とし、`正の表記｜定義｜コード識別子｜別名・禁止表記` を埋める。定義は公式ドキュメント・教科書で確認できる語義に留め、対応するコード識別子が無い概念は `—` とする。上位ドキュメントの内容（技術選定・配置・ビジネスルール）は復唱せず、用語の定義に徹する。
文体は `doc-writing-style` スキルの文体規範に従う（特に規範7：内容を復唱せず短い名前＋出典で参照する）。

### 5. 横断レビュー

単体レビュー（専用 reviewer による3周チェック）は行わない。006 を書き終えたら、CLAUDE.md のルールに従い `docs-integration-reviewer` エージェントを起動して横断レビューを実施し、結果をユーザーに提示する。特に観点4（用語の不統一）で、006 と 001〜005 の照合結果・006 への追記提案が返る。
