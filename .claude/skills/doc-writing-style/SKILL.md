# ドキュメント文体規範

本プロジェクトの永続ドキュメント（`docs/001_`〜`006_`）を書くときの文体を定める。
対象は**日本語の仕様ドキュメント**。技術書原稿向けのグローバル `japanese-tech-writing` skill とは別物なので、docs配下ではこちらを優先する。

守るべきは「読者が最短時間で正しく理解できること」。以下の8項目はすべてこの一点に向いている。

## 1. 明確さを最優先し、過度に圧縮しない

短くすること自体を目的にしない。冗長は削るが、削った結果として読者が文脈を補えなくなるなら削りすぎである。
目指すのは「短さ」ではなく「簡潔さと明確さの両立」。情報が落ちるくらいなら一文増やすほうがよい。

## 2. 擬似ジャーゴンを使わない

一般的な単語に独自の特別な意味を込めて、非一般的な文脈で使わない。読者が用語集（006_glossary.md）や一般常識から意味を回復できなくなる。

各分野で確立した技術用語はそのまま使ってよい。判断基準は「その語義が公式ドキュメントや教科書で確認できるか」。

- OK：コンパイラの「トークン」、DBの「正規化」、HTTPの「冪等」
- NG：「単語を*受肉*させる」のような、この文書でしか通じない比喩を定義なしに使う

## 3. 自明なことを書かない

丁寧に見せるためだけの説明を足さない。適切に名付けられた識別子・図・表がすでに語っていることを言い換えない。
「このセクションでは〜について説明します」のような、内容ゼロの前置きは削る。

## 4. 抽象的な主張には具体例を添える

一般論が抽象的すぎて解釈が割れる場合は、具体例を添える。「一般原則 ＋ 具体例」はドキュメントの理解を助ける有効な型である。

ただし例は代表的なものを選び、主張の適用範囲を不当に狭めないこと。エッジケースだけを例に出すと、読者はそれが唯一の適用場面だと誤解する。

## 5. 著者のトーンを保つ

汎用的な埋め草（「まず初めに」「ご存知の通り」「〜というのは非常に重要です」など、何も足さない定型句）は取り除く。
一方で、文脈が失われるほど短縮しない。原文の語り口・視点・粒度は維持する。推敲はリライトではなく、無駄を削る作業である。

## 6. 例の変数名は独立して読めるものにする

例中の変数名・識別子は、この会話やその場限りでしか意味を持たない名前を避ける。ドキュメント単体で読んだ第三者が理解できる一般的な名前にする。

命名は 006_glossary.md とグローバル命名規約（情報密度の高い動詞、単位付きの値名など）に従う。

- NG：`foo`、`tmp2`、直前の会話でだけ通じる `theThing`
- OK：`wordId`、`delay_ms`、`plaintext_password`

## 7. 曖昧な代名詞を避ける（ただし内容の複製で解決しない）

「これ」「それ」「その」「上記」が複数のものを指しうる箇所では、指示対象を名詞で明示する。
読者が一文戻って指示対象を探す必要が生じたら、その代名詞は書き換える。

ただし、指示対象が**他の節・他のドキュメントで定義済みの内容**（用語・仕様のリスト・ルールなど）である場合、その内容を丸ごと書き写して代名詞を解消してはならない。定義を復唱するとドキュメント間で二重管理になり、DRY 違反を招く。正しい解決は、指示対象を**短い名前で呼び、出典を指す**こと。明確さ（規約7）と単一情報源（DRY）は、この形で両立させる。

- NG（内容を複製して明示）：「JWT 検証（署名・exp・iss・client_id・token_use）のみ自前実装し」
- OK（短い名前＋出典を指す）：「JWT 検証（検証項目は 002）のみ自前実装し」

判断基準：明示しようとしている名詞が、他所に一次情報を持つ「定義済みの塊」なら、コピーせず参照する。純粋にその場の文の指示先を補うだけなら、そのまま名詞で明示してよい。

## 8. Markdownで強制改行を入れない

段落の途中でレンダリングを分断するハード改行を入れない。具体的には行末の半角スペース2つや `<br>` を使わない。
段落は連続した行として書き、意味の切れ目でのみ空行を挟んで段落を分ける。

## 使い方

ドキュメントを書き終えたら、この8項目を上から順に自己チェックする。
とくに 1・4・5 は「冗長を削りつつ文脈は残す」という同じ緊張のうえにあるので、削りすぎと足しすぎの両方向で見直すこと。
規約7 の代名詞明示は、他所で定義済みの内容を復唱していないか（＝DRY を壊していないか）を必ず併せて確認する。明示のために内容をコピーしていたら、出典参照へ置き換える。
