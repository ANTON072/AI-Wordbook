# テスト実装ガイド

テストフレームワークは vitest を使う。

## テスト方針

- **結合テスト優先**：ユーザーに見える振る舞い（APIレスポンス・ツールの戻り値・DBへの副作用）をテストする。結合テストでカバーできている範囲の単体テストは不要。
- **モック最小化**：モックは本物の依存を置き換えるため、テストと本番の乖離を生む。なるべく本物を使う。DB はモックせずテスト用 DynamoDB を使う。モックが許容されるのは、本物を用意するコストが著しく高い外部 API（Cognito 認証エンドポイントなど）に限る。モックを多用しないと成立しないテストは本物の振る舞いをほとんど検証していない — そのような場合はテストを書くこと自体を疑い、価値ある粒度・切り口に変える。
- **純関数の単体テスト不要**：純関数を使う機能があれば、その機能レベルのテストを書けばよい。例：`lib/normalize` の正規化ロジックを使う API ルートをテストすれば、`lib/normalize` 単体のテストは省略できる。
- **React サーバーコンポーネントのテスト不要**。
- **UI テスト不要**（現時点）。
- **カバレッジ計測不要**。点数を目標にしない。カバレッジを上げるためだけに、実質的な価値の低いテストを書くと、テストの保守コストがあがる。
- **コストに見合ったテストを選択する**: プロダクトにとって最もリスクの高い部分に対して、コストに見合った自信を得られるテストを選択すること。
- **Arrange-Act-Assert**: テストを書く際にはAAAパターン(Arrange-Act-Assert)を意識し、可読性を上げること。

Arrange-Act-Assertを意識した例:

```typescript
import { add } from "./add";

it("add関数がユーザーの年齢を加算して合計年齢を出す", () => {
  // Arrange:ユーザーの年齢情報を準備
  const userAge = 28;
  const friendAge = 32;

  // Act:関数を実行
  const totalAge = add(userAge, friendAge);

  // Assert:関数の結果を検証
  expect(totalAge).toBe(60);
});
```

- **エッジケースと境界値の洗い出し**: ハッピーパス以外にもエッジケースと境界値のテストを行うこと。
  - 文字列を処理する関数→空文字列や極端に長い文字列
  - 配列を扱う関数→要素数0の空配列
  - 数値計算の関数→0や負の数値、許容される最大値・最小値

## テスト対象の特定

`plan.md` の受け入れ条件を起点に「何を検証するテストが要るか」を導出する。受け入れ条件が検証可能な形になっていれば、そのままテストの名前になる。

| 実装の種類 | テストの種別と方針 |
|------------|-------------------|
| API ルート（`src/app/api/`） | Route Handler を直接呼び出し、レスポンスと DB 副作用を検証する |
| MCP ツール（`src/features/mcp/tools/`） | ツール関数を直接呼び出し、結果と DB 副作用を検証する |
| ビジネスロジック（`src/features/`・`src/lib/`） | 上位の結合テストでカバーできるなら不要。独立した複雑なロジックのみ単体テストも可 |
| UI コンポーネント | 不要（現時点） |

## テストファイルの配置

ロジックを持つファイルに `*.test.ts` を併置する（[004](../../../docs/spec/004_repository-structure.md) 参照）。

## DynamoDB Local と環境変数のセットアップ

結合テストの DynamoDB セットアップ・vitest での環境変数注入方法は [005 テスト戦略](../../../docs/spec/005_development-guidelines.md#テスト戦略) に記載されている（Docker 起動コマンド・`.env.test` の設定値・`src/test/setup.ts` での `loadEnvConfig` の使い方まで含む）。新規テストファイルを作成するときは先にその節を読む。
