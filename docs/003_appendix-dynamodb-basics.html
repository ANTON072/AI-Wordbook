付録：DynamoDB の考え方（RDB が分かる人向け）

「PK って Primary Key のこと？」から始めて、Partition Key / Sort Key・キーでしか引けない理由・このアプリのキー設計までを、RDB との対比と SVG 図で解説します。

このドキュメントが答えること：

  • PK は Primary Key ではなく Partition Key。主キーとの関係は？
  • なぜ Partition Key は「＝（等価一致）」でしか引けないのか
  • なぜ Sort Key だと前方一致（begins_with）が速いのか
  • このアプリの PK=userId, SK=word を RDB に翻訳すると？
  • なぜ Web 一覧の「登録日時降順」だけアプリ側で並べ替えるのか

0. まず用語の対応（RDB → DynamoDB）

「PK は Primary Key？」への答え PK は Partition Key（パーティションキー）の略です。Primary Key（主キー）は別概念で、 DynamoDB の主キーは Partition Key 単独か、Partition Key ＋ Sort Key の複合で作ります。 このアプリは後者（複合）で、PK と SK を合わせたものが主キーです。

1. Partition Key＝データを配る「宛先」

DynamoDB は1台の DB ではなく、内部でたくさんのサーバー（パーティション）に分散しています。どのパーティションに置くかは、Partition Key をハッシュ関数にかけて決めます。

図1：同じ userId は必ず同じパーティションに入る。だから「あるユーザーの全単語」はまとめて速く取れる。
代わりに失うもの：範囲・あいまい検索 ハッシュは「近い値どうしが隣に並ぶ」ことを保証しません（A1B2 と A1B3 が全然違う場所に飛ぶ）。 そのため Partition Key は userId = :値 の“ピンポイント指定”だけで、 userId LIKE 'A1%' のような範囲・前方一致はできません。

2. Sort Key＝同じ宛先の中での「並び順」

同じ Partition Key を持つアイテムは、1つのパーティションの中で Sort Key の順に並んで保管されます。並んでいるからこそ、範囲・前方一致（begins_with）が速く取れます。

図2：Sort Key で並んでいるので、re で始まる単語は連続した範囲として一気に取れる。これが search_words。

3. このアプリのキー設計を RDB に翻訳する

002 で決めた PK = userId ＋ SK = word は、RDB で書けばこうです。

-- DynamoDB の PK=userId, SK=word を RDB で書くと
CREATE TABLE Wordbook (
  userId    text,        -- Partition Key
  word      text,        -- Sort Key
  entries   jsonb,       -- 品詞・和訳・例文をまるごとJSON
  createdAt timestamptz,
  updatedAt timestamptz,
  PRIMARY KEY (userId, word)
);

4. 「引き方」が RDB と一番違う

RDB は好きな列で WHERE を書けますが、DynamoDB は基本キーでしか引けません。ここが最大の発想の差です。

図4：キー（Partition Key）を必ず伴う検索だけが速い。このアプリの検索は全て「あるユーザーの中」で完結するので Query だけで済む。
だから 003 に「GSI 不要」「Scan は付与しない」と書いてある このアプリの操作は「ログイン中のユーザー（＝PK が確定）」の中だけで完結します。 他人の単語を横断検索する機能はないので、追加の索引（GSI）も全走査（Scan）も要りません。IAM でも Scan 権限を与えません。

5. なぜ Web 一覧だけ「アプリ側で並べ替え」なのか

DynamoDB が返す順番は Sort Key（＝word）順で固定です。でも Web 一覧は「最近登録した順（createdAt 降順）」で見せたい。並び順の軸が違うので、DB では出せず、取得後にアプリ側で並べ替えます。

図5：search_words はアルファベット順でよいので DB の順のまま。Web 一覧は日時順にしたいのでアプリ側で並べ替える。
たとえ： 図書館の棚（DynamoDB）は背表紙のタイトル順（＝word 順）にしか並びません。 「最近借りた順で見たい」なら、いったん全部手に取ってから自分の手元で並べ替えるしかない。それがアプリ側ソートです。

6. まとめ（4行で）

  1. PK は Partition Key。PK＋SK が主キー（RDB の複合主キーに相当）。
  2. Partition Key はハッシュで分散させる宛先。「＝」でしか引けない（範囲不可）。
  3. Sort Key は同じ宛先内の並び順。前方一致・範囲が速い（＝search_words が GSI 無しで成立）。
  4. キーで引く Query だけが速い。だから全走査 Scan も追加索引 GSI も要らない設計にできる。並び順が違う Web 一覧だけアプリ側で並べ替える。

→ RDB の「どんな列でも WHERE で引ける」感覚を捨て、「キー設計＝アクセス方法の設計」だと考えるのが DynamoDB のコツです。
