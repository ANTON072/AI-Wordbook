付録：Web 認証の仕組み（Cognito の JWT を直接使う）

Web のログインを、認証ライブラリを使わず「Cognito が発行する JWT を HTTP-only Cookie に入れるだけ」で実装します。なぜこれで十分か、どう動くかを図解します。

このドキュメントが答えること：

  • Web はどうやってログインし、ログイン状態を保つのか
  • なぜ「ユーザーの ID がズレる」問題が起きないのか
  • MCP と Web で認証がどう共通化されているのか
  • 認証用のデータベースが要らないのはなぜか

0. 一番大事な前提：ID は Cognito の JWT に入っている

Cognito はログインに成功すると JWT（身分証トークン）を発行します。その中には、そのユーザーを表す一生変わらない背番号 sub が入っています。

たとえ： sub はあなた専用の棚の鍵番号。単語は DynamoDB の「sub の棚」に保管されます（詳しくは DynamoDB 付録参照）。 ログイン方式が MCP でも Web でも、同じ Cognito が同じ鍵番号（sub）の JWT を出すので、必ず同じ棚に着きます。
だから ID はズレない Web も MCP も「Cognito が発行した JWT の sub」をそのまま使います。間に独自の ID を作る仕組み（認証ライブラリ）を挟まないので、 「Web の ID と MCP の ID が食い違う」問題がそもそも発生しません。

1. 全体像：2つの入口、同じ JWT

図1：発行元は Cognito ひとつ。MCP も Web も同じ sub を使うので、同じユーザーは必ず同じ棚に着く。

2. Web のログイン手順（OAuth 認可コードフロー）

Web は「ログイン画面は Cognito に任せ、結果の JWT だけ受け取って Cookie に保存」します。手順はこうです。

図2：ログイン画面と本人確認は Cognito が担当。Next.js は最後に JWT を受け取って Cookie に入れるだけ。
state ってなに？（CSRF 対策） ②で送り、⑤⑥で照合する使い捨ての合言葉です。第三者が偽の認可コードを差し込む攻撃（CSRF）を防ぎます。行きと帰りで合言葉が一致しなければ弾きます。

3. ログイン後：毎回 Cookie の JWT を検証するだけ

一度 Cookie に JWT が入れば、以降のページ表示はシンプルです。DB にセッションを問い合わせる必要はありません（＝ステートレス）。

図3：Cookie の JWT を検証して sub を得て、そのまま Query。認証用 DB へのアクセスは無い。

4. MCP と Web の比較（ほぼ同じ）

MCP（Claude Desktop）Web（ブラウザ）
JWT の入手OAuth 2.0 PKCE で取得OAuth 認可コードフローで取得
JWT の運び方Authorization: Bearer …HTTP-only Cookie
検証（署名・exp・iss・token_use）同じ jose モジュールを共用 ✔
client_id の期待値COGNITO_MCP_CLIENT_IDCOGNITO_WEB_CLIENT_ID
ユーザー識別JWT の sub をそのまま使う
1点だけ注意：client_id の期待値は経路で違う 署名・有効期限などの検証は完全に共通ですが、client_id（トークンを発行したアプリの ID）だけは経路で異なります。 MCP 用と Web 用で Cognito のアプリクライアントを2つ作るためです。検証関数には「期待する client_id」を引数で渡して切り替えます。

5. なぜこの方式がシンプルなのか

認証ライブラリ（Better Auth 等）を使う場合と比べ、次のものがまるごと不要になります。

  • ❌ 認証用のデータベーステーブル（セッション保存）
  • ❌ ライブラリ独自のユーザー ID 管理（→ sub とのズレ調整も不要）
  • ❌ DB アダプタの実装

代わりに使うのは Cognito の標準エンドポイント2つ（/oauth2/authorize・/oauth2/token）と Cookie、そして MCP と共通の JWT 検証だけ。学習の本筋（OAuth・JWT 検証を自作する）にも沿います。

まとめ（3行で）

  1. Cognito が発行する JWT に sub が入っている。Web も MCP もこれを使うので ID はズレない。
  2. Web はログインを Cognito に任せ、返ってきた JWT を HTTP-only Cookie に入れるだけ（DB セッション不要）。
  3. 以降は毎回 Cookie の JWT を検証して sub を取り出し、Query(PK=sub) する。検証は MCP と共通（client_id の期待値だけ経路で切替）。
