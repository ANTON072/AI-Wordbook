# リポジトリ構造定義書

## 概要

### PRD・機能設計書・技術仕様書との対応関係

本書は技術仕様書(003)が「どう構成するか＝ディレクトリ構造は 004 に委譲」と明記した物理配置を、新しいファイル・ディレクトリを作る前に置き場所を迷わず決められるレベルまで具体化する。

前提はすべて上位ドキュメントで確定済みであり、本書では繰り返さない。すなわち PRD(001) の機能スコープ、機能設計書(002) の論理設計（コンポーネント責務・データフロー・キー設計・MCP ツール IF）、技術仕様書(003) の技術スタック選定（単一 Next.js アプリ・単一サーバー Lambda・DynamoDB 単一テーブル・Web/MCP 共用モジュール）を正として前提にする。本書が担うのは、その構成を「どのディレクトリ・ファイルに置き、依存をどの向きに流すか」だけである。

### 構造定義スコープ

- 対象：トップレベルのディレクトリツリー、各ディレクトリの責務、新規ファイルの配置ルール、モジュール依存の方向、テスト・設定・ドキュメントの配置
- 対象外（005 開発ガイドラインに委譲）：コーディング規約、コンポーネントの内部設計・CSS 設計、テスト戦略（単体／統合の範囲・カバレッジ方針）
- 対象外（006 ユビキタス言語に委譲）：識別子・用語の命名語彙
- 対象外（003 に既定）：技術・ライブラリの選定とその根拠
- 対象外（002 に既定）：ユースケース、画面設計、データフロー、MCP ツールのインターフェース仕様

**本書はディレクトリと配置ルールを定義し、末端の個別ファイルは列挙しない。** ファイルは実装で増減するため、1 ファイル追加のたびに本書を改訂せずに済ませ、構造の恒久性を保つ。どのファイルをどこへ置くかは、後述の配置ルールと依存方向から一意に決まる。

## ディレクトリツリー全体像

003 が確定した「Web 閲覧画面と MCP サーバーを同一の Next.js アプリに統合し、OpenNext が単一サーバー Lambda にバンドルする」構成に従い、リポジトリは**単一の Next.js プロジェクト**である。モノレポにもフロント／バックエンド分離にもしない。

以下はディレクトリの骨格であり、末端ファイルの網羅ではない（フレームワークが名前を固定する `route.ts`・`page.tsx` 等と、位置づけを示す代表ファイルのみ記す）。

```
ai-wordbook/
├─ sst.config.ts                # SST v3 のインフラ定義（技術スタック・IAM・環境変数は 003）
├─ next.config.ts
├─ tsconfig.json
├─ vitest.config.ts
├─ postcss.config.mjs           # Tailwind（Next.js 標準セットアップ）
├─ package.json
├─ .gitignore
├─ docs/                        # 永続ドキュメント（001〜004 が既存、005・006 は今後追加）
└─ src/
   ├─ middleware.ts             # 入口層。Web 保護ルートの未認証リダイレクト（保護範囲・参照は「モジュール依存の方向」）
   ├─ app/                      # App Router：ルーティングとルート固有 UI
   │  ├─ layout.tsx
   │  ├─ globals.css            # Tailwind エントリ
   │  ├─ login/                 # /login：Hosted UI へのリダイレクト起点
   │  ├─ wordbook/              # /wordbook（一覧）・/wordbook/[word]（個別）。ルーティング仕様は 002
   │  │  └─ _components/        # このルート専用 UI（一覧・モーダル・両者が共有する詳細表示）
   │  ├─ api/                   # Route Handler（mcp・auth/callback）。薄く保ち features へ委譲
   │  └─ .well-known/           # MCP OAuth ディスカバリの Route Handler。features/mcp へ委譲
   ├─ features/                 # このアプリ固有の振る舞い（ロジック・データ取得）
   │  ├─ mcp/                   # MCP：リクエストパイプライン組み立て
   │  │  └─ tools/              # register/delete/update/search を 1 つ 1 ファイル
   │  ├─ auth/                  # Web の OAuth 認可コードフロー・セッション（sub 解決）
   │  └─ wordbook/              # Web 閲覧の読み取り（書き込みを持たない根拠は「配置ルール」）
   └─ lib/                      # 機能横断プリミティブ（ビジネス知識を持たない）
      └─ normalize・auth・db・schema・types・url    # 各関心（役割は下表）。単一ファイルはフラット、複数化でディレクトリ昇格
```

## ディレクトリ責務

`src/` は 3 つの関心に分かれる。この 3 分割が、新規ファイルをどこに置くかの一次判断軸になる。

| ディレクトリ | 責務 | 判定基準 |
| --- | --- | --- |
| `src/app/` | Next.js App Router のルーティングと、そのルート専用の UI コンポーネント | 画面・URL・UI か。ルート専用 UI はそのルート配下の `_components/` にコロケーションする |
| `src/features/` | このアプリ固有の振る舞い（ユースケースを実現するロジック・データ取得） | このアプリの仕様を encode しているか（例：register_word の冪等登録、Web 一覧の createdAt 降順取得） |
| `src/lib/` | ビジネス知識を持たない機能横断プリミティブ | 単語帳という題材を知らなくても再利用できるか（例：正規化、JWT 検証、DynamoDB クライアント） |

**Route Handler は薄く保つ。** `api/mcp`・`api/auth/callback`・`.well-known/oauth-protected-resource` のいずれの Route Handler も、リクエスト受付と対応する `features/` 呼び出しの結線のみを担い、振る舞いを持たない。

`features/` の各機能の責務は以下。

| `features/` | 責務 |
| --- | --- |
| `mcp/` | MCP サーバー。`lib/auth`・`lib/normalize`・`lib/schema` を束ねてリクエストパイプラインを組み立てる（各ステップと順序は 002）。パイプライン組み立てが `features/mcp` の中核責務であり、Route Handler には置かない。ツールハンドラ（register/delete/update/search を 1 つ 1 ファイル、`tools/` 配下）は永続化に徹する。`.well-known` が返すディスカバリメタデータの組み立ても持つ |
| `auth/` | Web の OAuth 認可コードフロー（Cognito 往復・`state` 生成・`state` 検証・Cookie 発行）と、Cookie 内 JWT から `sub` を解決するセッション処理。`app/login/` は起点として `features/auth` を呼ぶだけで、`state` 生成はこちらが持つ |
| `wordbook/` | Web 閲覧の読み取りのみ（取得方式は 002）。書き込みは持たない |

`lib/` の各関心の役割は以下。

| `lib/` | 役割 |
| --- | --- |
| `normalize/` | 単語正規化の単一実装（ルールは 002。Web・MCP 共用） |
| `auth/` | JWT 検証コア（検証項目は 002、`client_id` 期待値のみ引数で切替） |
| `db/` | DynamoDB DocumentClient（初期化位置と再利用の根拠は 003） |
| `schema/` | zod スキーマ（`WordInput`／`Entry`／`Example`／`prefix`。型定義は 002） |
| `types/` | 共有型（`schema` から `z.infer` で導出＋非検証型。定義元は 002） |
| `url/` | 個別ページ URL 組み立て（URL 形式は 002。`APP_BASE_URL` 基点） |

`lib/auth` と `features/auth` の切り分けは、上の判定基準がそのまま効く。JWT 検証コアはアプリ知識を持たない汎用処理なので `lib/auth`、Cognito との OAuth 往復・`state` 検証・Cookie 発行はこのアプリの認証手順なので `features/auth` に置く。

`src/middleware.ts` は `app/` と同じ**入口層**として扱う。責務は Web 保護ルートの未認証リダイレクトに絞り、存在ゲートに徹するため参照は `lib/auth`（JWT 検証コア）のみに限る。

## 配置ルール

新規ファイルは以下の順で置き場所を決める。

1. **UI コンポーネントか** → そのルート配下の `app/.../_components/` にコロケーション。同一ルートセグメント内で複数の画面が共有する UI（例：一覧のモーダルと個別ページが共有する詳細表示）も、そのセグメントの `_components/` に置く。**別のルートセグメントをまたいで**共有する純粋な表示部品が生じて初めて `src/components/` を新設する。
2. **このアプリ固有の振る舞いか** → `features/<機能>/` に置く。機能は `mcp` / `auth` / `wordbook` の 3 つ。
3. **ビジネス知識を持たない横断プリミティブか** → `lib/<関心>/` に置く。関心は `normalize` / `auth` / `db` / `schema` / `types` / `url`。関心が単一ファイルで収まる間は `lib/url.ts` のようにフラットに置き、複数ファイルに増えたらディレクトリへ昇格する。

加えて、003 の設計上の制約を構造として固定する。

- **書き込み操作は `features/mcp/tools/` のみが持つ。** DynamoDB への `PutItem`／`UpdateItem`／`DeleteItem` を発行するコードはツールハンドラに限定し、`features/wordbook`（Web 閲覧）は読み取り（`Query`／`GetItem`）しか持たない。003 が「Web からの単語書き込み抑止はアプリ層で保証する」と定めた責務を、置き場所の分離として物理的に担保する。
- **`userId`（PK）は検証済みトークン由来の `sub` を渡す。** `features/` の各関数はクライアント入力から `userId` を受け取らず、`lib/auth` の検証結果として得た `sub` を引数で受ける。003 の「ユーザー間データ分離はアプリ層で保証」に対応する。
- **単語正規化は `lib/normalize` の 1 実装だけを参照する。** MCP のツール入力も、Web 個別ページの URL デコード後の突き合わせも、同一実装を通す（002 が求める Web/MCP 共通化）。
- **MCP ツールは 1 つ 1 ファイル**にし、`features/mcp/tools/` 配下に置く。ツールが増減しても本書の改訂は要らない（配置はこのルールで決まる）。

## モジュール依存の方向

依存は `app → features → lib` の一方向に流す。

- `lib/` は葉であり、`app/` にも `features/` にも依存しない。単語帳ドメインを知らない汎用コードだけを置くことで、この方向を保てる。
- `features/` は `lib/` にのみ依存し、`app/` を参照しない。UI やルーティングを知らずにテストできる。
- `features/` 間の相互依存は避ける。機能をまたぐ結線は**呼び出し側**で行う。呼び出し側とは、書き込み系なら `app/` の Route Handler、Web 閲覧系なら Server Component（`app/wordbook/page.tsx`）である。たとえば一覧表示は、Server Component が `features/auth`（`sub` 解決）と `features/wordbook`（一覧取得）を結線する。
- 共有が必要になった処理は、ビジネス知識を持たないなら `lib/` へ引き上げ、持つなら上記の呼び出し側で結線する。
- `lib/auth`（JWT 検証コア）は Web 経路と MCP 経路の両方から参照される共通の葉である。Web 経路では 2 つの役割で使う——`middleware.ts` が未認証をはじく**存在ゲート**として、`features/auth` のセッション処理が実データ取得のための **`sub` 抽出**として。どちらも `lib/auth` の単一実装を通すため検証ロジックは重複しない。両経路・両役割の違いは `expectedClientId` 引数だけで、実装は分岐しない（切替の詳細は 003）。
- `middleware.ts` の保護対象は Web ルート（`/wordbook`・`/wordbook/[word]`）に限定し、`/api/*`・`.well-known/*`・`/login` は除外する。MCP（`/api/mcp`）は Cookie を持たない Bearer 認証のため、middleware でリダイレクトすると認証が壊れる。

## テスト・設定・ドキュメントの配置

- **単体テスト**：対象ファイルと同居する（`*.test.ts` を隣に置く）。テスト対象との参照距離を近く保ち、移動・削除時に追従しやすくする。単体／統合の範囲・カバレッジ方針は 005 に委ねる。
- **モジュールをまたぐテスト**：colocation で吸収できない統合／E2E テストが 005 の方針で必要になった場合は、`tests/` 直下に置く（要否・範囲の判断は 005、物理配置のみ本書が定める）。
- **設定ファイル**：`sst.config.ts`・`next.config.ts`・`tsconfig.json`・`vitest.config.ts`・`postcss.config.mjs`・`package.json` はすべてリポジトリルートに置く。単一プロジェクトのため設定は 1 セットで足りる。
- **シークレット**：Cognito Web クライアントシークレット等はリポジトリにコミットせず SST の `Secret` で管理する（管理方針は 003）。ローカル用の環境変数ファイルは `.gitignore` 対象とする。
- **ドキュメント**：永続ドキュメントは既存の `docs/` にとどめる（001〜004 が既存、005・006 は今後追加）。

## 構造上の確定事項と根拠

| 決定 | 根拠 |
| --- | --- |
| 単一 Next.js プロジェクト（モノレポにしない） | 003：Web 閲覧と MCP を同一アプリに統合し OpenNext が単一 Lambda にバンドルするため、プロジェクトを分ける理由がない |
| 全アプリコードを `src/` 配下に置く | ルート直下の設定ファイル群とアプリコードを分離し、トップレベルを見通しやすくする |
| `app / features / lib` の 3 分割 | 「UI／このアプリ固有の振る舞い／横断プリミティブ」という配置判断の一次軸を、ディレクトリ境界として可視化する。レイヤードアーキテクチャのような重い抽象は 5 名規模の学習プロジェクトに不要なため採らない |
| 依存方向を `app → features → lib` の一方向に固定 | 循環依存と層の逆流を防ぎ、`lib`・`features` を UI から切り離してテスト可能にする |
| MCP のリクエストパイプラインを `features/mcp` が組み立て、Route Handler は薄く保つ | JWT 検証フローの自力実装が PRD の学習対象。中核ロジックを features に集約し、Route Handler の framework 都合と分離する |
| 書き込み操作を `features/mcp/tools/` に限定 | 003 の「Web からの単語書き込み抑止はアプリ層で保証」を、置き場所の分離として構造的に担保する |
| UI・テストのコロケーション | ルート専用 UI とテストを対象の近くに置き、変更時の追従性を高める |
| ディレクトリと配置ルールのみ定義し、末端ファイルは列挙しない | ファイル追加のたびに本書を改訂せずに済ませ、構造定義の恒久性を保つ |
