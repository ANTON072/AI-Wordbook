# 開発ガイドライン

## 概要

### PRD・機能設計書・技術仕様書・リポジトリ構造定義書との対応関係

本書はリポジトリ構造定義書(004)が「コーディング規約・コンポーネントの内部設計/CSS 設計・テスト戦略は 005 に委譲」と明記した領域を、実装者がコードを書くときに「どう書くか」を迷わず判断できるレベルまで具体化する。

前提はすべて上位ドキュメントで確定済みであり、本書では繰り返さない。技術・ライブラリの選定と根拠は 003、ディレクトリの物理配置・モジュール依存の方向・テストの配置は 004、識別子と用語の命名語彙は 006、ユースケース・データフロー・キー設計・ビジネスルールは 002 が正である。本書が担うのは、その前提の上でコードをどう書くか、だけである。

### ガイドラインスコープ

- 対象：コーディング規約（型の扱い・エラーハンドリング・非同期処理の作法）、コンポーネント設計（内部設計・CSS 設計）、テスト戦略（単体／統合の範囲・カバレッジ方針）
- 対象外（003 に既定）：技術・ライブラリの選定とその根拠。lint/formatter・パッケージマネージャの**選定**も 003 に属し、本書は選定済みのツールを**どう使うか**だけを定める
- 対象外（004 に既定）：ファイル・ディレクトリの物理配置、モジュール依存の方向、テストコードの配置
- 対象外（006 に委譲）：識別子・用語の命名語彙
- 対象外（002 に既定）：ユースケース、画面設計、データフロー、ビジネスルール

**本書の最上位原則：機械で強制できるものは条文化しない。** biome の lint/format と `tsconfig` の strict 設定で機械的に検出・矯正できるものは、本書に規約として書かずツール設定に委ねる。本書に書くのは、ツールで縛れない・人間の判断が要る規約に限る。5 名規模の学習プロジェクトで守られ続ける軽さを保つためである。

## コーディング規約

### ツールへの委譲

以下はツールが強制し、本書では個別条文にしない。

- **整形・import 順・基本的な lint** — biome に委ねる（選定・バージョン方針は 003）。行幅・クォート・セミコロン・未使用変数などの機械判定は biome の設定が単一の正であり、本書で重複して規定しない。
- **型の厳格さ** — `tsconfig` の strict を有効にし、コンパイラに強制させる。
- **依存関係の一貫性** — パッケージマネージャは pnpm（選定は 003）。`pnpm-lock.yaml` のみをコミットし、`package-lock.json`／`yarn.lock` を混在させない。
- **React のコードスタイル・ファイル名** — Next.js 公式が推奨するスタイルに従う（関数コンポーネント、Hooks の規則、`route.ts`／`page.tsx` 等の命名慣習）。公式で確認できる規約は本書で復唱しない。命名語彙は 006。

### 型の扱い

- **`any` は原則使わない。** 許可するのは、ライブラリの型が不必要に複雑で `any` 以外の記述が費用に見合わないケースに限る。使う箇所には理由を 1 行コメントで残す。それ以外の未知の値は `unknown` で受け、絞り込んでから使う。
- **単語データ型は zod スキーマから導出する。** `WordInput`／`Entry`／`Example` 等の型は `lib/schema` の zod スキーマから `z.infer` で導く（スキーマ定義元は 002、物理配置は 004）。同じ構造を手書きの型として二重定義しない。

### エラーハンドリング

エラーの種別ごとの HTTP ステータスと Claude への返却内容は 002 のエラーハンドリング方針が正である（本書では復唱しない）。本書が定めるのは、その方針を**どこで・どう実装に落とすか**である。

- **ツールハンドラ・データ取得関数は整形を持たない。** `features/mcp/tools/` のツールハンドラと `features/` の各関数は、失敗を例外として投げる（または失敗を表す戻り値を返す）ことに徹し、レスポンスの整形を持たない（004 の「ツールハンドラは永続化に徹する」と整合）。
- **整形の境界は経路ごとに分かれる。** MCP 経路では `features/mcp` のリクエストパイプラインが失敗を捕捉し、002 のエラー方針へ整形する（パイプライン組み立てが `features/mcp` の責務である根拠は 004）。Web 認証経路では `features/auth` が `state` 検証失敗・トークン交換失敗を例外として投げ、Route Handler がそれを捕捉してエラーページへのリダイレクト（または HTTP ステータス）に変換する。Web 経路には 002 の Claude 向けエラー契約は適用しない。Route Handler が担うのは例外から HTTP 応答への変換という結線であり、004 の「Route Handler は振る舞いを持たない」と両立する。いずれも整形箇所を 1 つに集約し、ハンドラ側に散らさない。
- **バリデーション失敗の変換** — zod の検証失敗は上記の整形境界で捕捉し、どのフィールドがなぜ失敗したかを含む自然言語メッセージに変換して返す（ステータスの区分は 002）。zod のエラーオブジェクトをそのまま Claude へ渡さない。
- **捕捉できない失敗** — Lambda タイムアウト等、アプリ層で整形できない失敗は 002 の方針どおりインフラ側の応答に委ね、握りつぶさない。

### 非同期処理とデータ取得

- 非同期は `async`/`await` で書き、生の Promise チェーンを混在させない。
- **データ取得は Server Component で行う。** 取得済みデータは props で Client Component へ渡し、Client Component からのデータ取得（クライアント fetch）は行わない。Web 閲覧は読み取りのみで、取得方式は 002・003 が正である。
- **`userId`（PK）はクライアント入力から受け取らず、検証済みトークン由来の `sub` を引数で渡す**（ユーザー間データ分離の根拠と配置は 003・004）。

## コンポーネント設計

### 内部設計

- **既定は Server Component とし、`'use client'` はインタラクションを持つ葉に閉じる。** クライアント境界を持つのは、状態やイベントを扱うコンポーネント（一覧上のモーダル開閉、検索入力など）に限る。ページ全体を安易に Client Component にしない。
- **クライアント状態は UI 状態に限る。** モーダルの開閉・検索語の入力状態など、画面操作に閉じた状態だけを `useState` で持つ。サーバーから取得したデータはクライアント状態に写し替えず、props で下ろして参照する。グローバル状態管理ライブラリは導入しない（小規模のため不要）。
- **分割は重複が生じてから行う。** ルート専用 UI は 004 のコロケーション方針に従って配置する。同一ルート内の複数画面が共有する表示（一覧のモーダルと個別ページが共有する詳細表示）は共通コンポーネントに切り出すが、まだ 1 箇所でしか使わない表示を将来を見越して先に抽象化しない。

### CSS 設計

- **デザインの源泉は Claude Design が作成した成果物とする。** 実装者はその成果物を Tailwind で忠実に再現し、独自の意匠を足さない。成果物の所在は未確定であり、確定後に本項へ追記する。所在が確定するまでは、002 の画面仕様を UI 実装の唯一の根拠とする。
- **レイアウトは配置の次元で選ぶ。** 2 次元（行と列）の配置・整列は CSS Grid（Tailwind の `grid` ユーティリティ）、1 次元（一方向の並び・折り返し）は Flex で組む。既定は Grid とし、Flex は 1 次元配置に収まる箇所で選ぶ。
- **Tailwind クラスの並び順・書き方に規約は設けない。** クラスの整列は biome／エディタの整形に委ね、本書では縛らない。
- **共通化は素朴に始める。** まずクラスをそのまま並べ、同じクラス列の繰り返しが保守を妨げる段階になって初めて、コンポーネント抽出で解消する。`@apply` や独自ユーティリティによる先回りの抽象化はしない。

## テスト戦略

### テストの範囲（単体・統合）

**結合テストを重視し、単体テストは純ロジックに絞る。無駄なテストは書かない。** テスト対象は「振る舞いのある境界」に限定する。テストコードの配置は 004 のコロケーション方針に従う。テストランナーは vitest（選定は 003）。

テストする対象：

| 対象 | 種別 | 見るもの |
| --- | --- | --- |
| 単語正規化（`lib/normalize`） | 単体 | 002 の正規化ルールを満たすか |
| バリデーション（`lib/schema` の zod） | 単体 | 002 のバリデーション規則で正しく通過／棄却するか |
| JWT 検証（`lib/auth`） | 単体 | 検証項目（項目は 002）を満たすか。`expectedClientId` 引数による経路別の期待値切替が効くか |
| 4 つの MCP ツール（`features/mcp/tools/`） | 結合 | register の冪等（`attribute_not_exists`）・update/delete の存在前提（`attribute_exists`）の分岐を含む CRUD が、実際の DynamoDB 操作として成立するか |
| Web 認証コールバック（`features/auth`） | 結合 | `state` 検証（CSRF 対策）が改ざんを弾くか |

- **結合テストの DynamoDB は DynamoDB Local を使う。** 実際の `Query`／`PutItem` と条件式（`attribute_not_exists`／`attribute_exists`）の振る舞いまで検証する。クライアント応答をモックで差し替える方式は、条件式や実クエリの挙動を検証できないため採らない。テスト用の実 AWS テーブルも使わない（認証情報・後始末のコストに見合わない）。DynamoDB Local の起動・接続設定は vitest のセットアップに集約する。

テストしない対象：外部 SDK の薄いラッパー、自明なアクセサ、UI の見た目、Next.js やライブラリ自体の挙動。これらは振る舞いを持たないか、フレームワーク／ライブラリ側が保証するため、テストの価値がコストを下回る。

### カバレッジ方針

**カバレッジ数値目標は置かない。** 到達率を指標にすると、価値の低いテストを数合わせで書く誘因になる。判断基準は「上記の振る舞いのある境界が試験されているか」であり、行網羅率ではない。

## 確定事項と根拠

| 決定 | 根拠 |
| --- | --- |
| 機械で強制できるものは条文化せず、biome・`tsconfig` strict に委ねる | 学習プロジェクトで守られ続ける軽い規約に保つ。ツールと文書の二重管理を避ける |
| lint/formatter は biome、パッケージマネージャは pnpm（いずれも選定は 003） | 本書は選定済みツールの「どう使うか」に徹し、選定根拠は 003 に置く |
| `any` は限定許可（ライブラリ型が過度に複雑な場合のみ・理由コメント必須） | 実務上の逃げ道を残しつつ、理由明示で乱用を防ぐ。通常の未知値は `unknown` で受ける |
| 単語データ型は zod スキーマから `z.infer` で導出 | 型とスキーマの二重定義による齟齬を防ぐ（定義元は 002） |
| 整形は経路ごとの単一境界に集約（MCP は `features/mcp` パイプライン、Web 認証は Route Handler） | ツールハンドラに整形を散らさず、004 のパイプライン責務・Route Handler 配置と整合させる |
| 既定は Server Component、`'use client'` は葉に限定 | Next.js 公式推奨に沿い、クライアント境界を最小化する。小規模のためグローバル状態管理は持たない |
| レイアウトは配置の次元で選ぶ（2 次元＝Grid・1 次元＝Flex、既定は Grid） | 配置次元で機械的に選べるようにし、選択の揺れを減らす |
| 結合テスト重視・DynamoDB Local を使用 | 条件式（冪等・存在前提）の分岐という本アプリの要は、実クエリの振る舞いでしか担保できない |
| カバレッジ数値目標を置かない | 到達率目標が誘発する数合わせテストを避け、振る舞いの試験に集中する |
